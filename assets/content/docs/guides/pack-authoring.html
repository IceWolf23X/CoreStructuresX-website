How packs work

A pack is a graph of reusable schematic modules. The first module comes from start.group; CONNECTOR markers name the group used for each next edge. A candidate is selected by weight only after the runtime confirms its configured safety checks.

Plan the module graph

Begin with one entrance, one repeatable path and one endpoint. Draw every connector group and its route to an endpoint. Add fallback candidates where tight terrain can reject a normal module, and add endpoint-only closing groups for connectors that may remain open at a hard limit.

Folder layout

plugins/CoreStructuresX/packs/abandoned_mine/
|-- pack.yml
|-- structure.yml
|-- groups.yml
|-- commands.yml
`-- schematics/
    |-- entrance_01.schem
    |-- corridor_01.schem
    `-- endpoint_01.schem

commands.yml is optional when no schematic has a COMMAND marker. All configured paths must stay inside this pack directory.

Create schematics

  1. Build one module with an intentional bounding box.
  2. Place zero or one ORIGIN marker; save the clipboard origin deliberately when omitting it.
  3. Place each CONNECTOR at the exact attachment point and face it toward the child expansion direction.
  4. Add COMMAND markers only for trusted post-placement actions.
  5. Save as Sponge .schem through the provider used by the target server.

Test block-state rotation and block-entity NBT for chests, signs, skulls, banners, spawners and lecterns. Enable schematic entities only after testing their position, rotation and state on the exact stack.

Marker signs

Use only ORIGIN, CONNECTOR and COMMAND. Marker blocks are replaced during paste, while the connector, trigger and command records are persisted. See the complete line contract.

pack.yml

Set schema version 1, a unique safe id, display metadata, and the relative filenames for structure, groups, commands and schematics. A folder/id mismatch is allowed with a warning; duplicate declared ids disable every duplicate pack.

structure.yml

Match the pack id. Keep start.mode: MANUAL, choose a start group and native facing, then configure placement offset, generation mode, limits, completion, checks and paste behavior. Keep backtrack-on-blocked: false and require-all-connectors-resolved: true.

groups.yml

Each dynamic group needs at least one positive-weight entry. Optional per-entry offset replaces the pack offset for that candidate. Marker replacement overrides apply only to that entry. Fallback and closing references must name existing groups; closing entries must have zero CONNECTOR markers.

commands.yml

Each command group contains positive-weight entries. An entry may hold one string, a list, or a map of named strings. Commands run as console after the at-most-once reservation is saved. Do not place untrusted input into administrator-authored commands.

Safety choices

  • Keep one active job per instance until serial execution is proven.
  • Use a conservative replaceable-block whitelist.
  • Enable double pass only with block checking; it never bypasses pending jobs.
  • Start lookahead at depth 1 and increase only with measured need.
  • Keep module, radius, connector and global schematic limits well below accidental input sizes.
  • Use post-paste replacements for deliberate temporary authoring blocks.

Validate and test

/csx reload
/csx validate pack abandoned_mine
/csx packs list
/csx start abandoned_mine world 100 64 100 SOUTH
/csx instance info <instance-id>

Test every rotation, branch, fallback, closing route, mode, limit transition and restart. A first module that pastes correctly does not prove the complete graph.

Common failures

  • Missing pack: check direct folder placement, pack.yml, unique id and confined paths.
  • Invalid schematic: check markers, group ids, provider readability and configured size limits.
  • Blocked connector: inspect the recorded reason, fallback/closing graph, overlap, whitelist and lookahead.
  • Stalled automatic mode: inspect TPS, MSPT, stable samples, job delay and closing state.
  • Inactive proximity: check the same world, the connector state and a positive explicit/default radius.

Release checklist

  • Zero validation errors.
  • All reachable groups have a finite endpoint route.
  • All rotations preserve expected block states and NBT.
  • Optional entities are proven on the target stack.
  • Largest intended expansion remains inside every hard limit and runtime budget.
  • Interrupted trusted jobs resume after a clean restart.
  • World and plugin folders are backed up before production use.
