Pack authoring guide

Build a structure pack from the first schematic to a validated live test.

This guide explains how modules connect, what every marker and YAML file controls, how fallback and closing paths work, and how to test a pack without leaving unresolved connectors or unsafe paste settings.

Mental model

A pack is a graph of reusable schematic modules.

An administrator starts one structure instance from the pack's start group. CoreStructuresX selects a weighted schematic from that group, pastes it, discovers its marker signs, and persists the resulting module, connectors, triggers, commands, and paste journal in instance JSON.

Every CONNECTOR marker names the group that may provide its child module. That child is rotated and positioned by aligning its ORIGIN with the connector position plus the configured offset. A connector is one-shot: it becomes processing while its job is active, then used or closed after successful finalization.

start.group
  -> entrance_01.schem
      -> CONNECTOR "corridor"
          -> corridor group: straight, corner, room, split
              -> fallback group when normal candidates cannot fit
              -> closing group with zero-connector endpoints

The pack files define future choices. Live instances are separate persisted state. Do not edit a pack or reload it while a paste job is queued, running, paused, or finalizing.

Before building

Plan the module graph before writing YAML.

  1. Choose one pack id, such as abandoned_mine. Use the same id in the folder, pack.yml, and structure.yml.
  2. Choose a start group and at least one entrance schematic.
  3. List the reusable connector groups: for example corridor, room, stairs, or branch. These names are authored by you; they have no built-in meaning.
  4. Decide which smaller modules can act as fallbacks when a preferred candidate overlaps terrain or another module.
  5. Create endpoint schematics with zero CONNECTOR markers. Closing groups may contain only these endpoint modules.
  6. Decide whether every open connector must continue automatically or wait for a nearby player.

Begin with one entrance, one repeatable path module, and one endpoint. Validate that small graph before adding rooms, splits, stairs, commands, lookahead, or parallel jobs.

Pack directory

Create the required files under the configured packs folder.

plugins/CoreStructuresX/packs/abandoned_mine/
|-- pack.yml
|-- structure.yml
|-- groups.yml
|-- commands.yml          # required only when COMMAND markers are used
`-- schematics/
    |-- entrance_01.schem
    |-- corridor_01.schem
    |-- corridor_small_01.schem
    `-- collapsed_end_01.schem

Each pack contains exactly one pack.yml, one referenced structure file, one referenced groups file, and one schematics directory. Duplicate pack ids are invalid. A folder name different from the pack id can load with a warning, so matching them is the safest convention.

WorldEdit or FAWE

Author each module as a deliberate bounding box.

  1. Build the complete module in a staging world, including ordinary block entities such as containers, decorative signs, spawners, skulls, banners, or lecterns that must survive the paste.
  2. Place the CoreStructuresX marker signs described below. Prefer one explicit ORIGIN in every schematic.
  3. Make every connector sign face outward in the direction where the child module should grow. Do not write directions or dimensions on the sign.
  4. Select only the volume the module needs and save it as a Sponge .schem through WorldEdit or FAWE.
  5. Copy the file into the pack's schematics/ directory and reference that exact filename in groups.yml.

Overlap checks use the full schematic dimensions, including selected air, rather than only non-air blocks. Excess selection space can therefore reject placements that look visually empty.

If no explicit ORIGIN exists, CoreStructuresX uses the clipboard origin saved in the schematic. Multiple origin markers are always invalid. If the saved origin already includes spacing outside the selection, avoid applying the same distance again through placement.offset.forward.

Block-entity NBT is preserved for non-marker blocks. Schematic entities are optional and require performance.paste.paste-entities: true; test their position, rotation, and NBT on the exact Paper and WorldEdit/FAWE versions used in production.

Sign contract

Use only the three supported marker types.

ORIGIN

[CSX]
ORIGIN

Recommended once per schematic. It is the alignment point for child placement. Line 3 is ignored.

CONNECTOR

[CSX]
CONNECTOR
corridor
16

Line 3 is a group id from groups.yml. Optional line 4 is a positive proximity radius. The sign facing defines expansion direction.

COMMAND

[CSX]
COMMAND
spawn_loot
8

Line 3 is a command group from commands.yml. Optional line 4 controls its proximity trigger.

  • Line 1 must match the configured marker header; matching is case-insensitive by default.
  • Do not use aliases such as CONN, SPAWN, ENTRY, EXIT, ROOM, or NODE.
  • A blank line 4 uses the pack default radius in PLAYER_PROXIMITY mode. A nonblank zero, negative, or malformed value is invalid.
  • Every proximity connector needs either an explicit positive radius or a positive pack default.
  • Marker blocks are replaced during paste. Connectors and triggers continue from JSON even after the sign disappears.

Pack manifest

Describe the pack and point to its files.

pack-version: 1
id: abandoned_mine
name: "Abandoned Mine"
version: "1.0.0"
author: "YourName"
structure: structure.yml
groups: groups.yml
commands: commands.yml
schematics-folder: schematics
  • pack-version must be 1.
  • The id must be filesystem-safe and unique across loaded packs.
  • Referenced files and the schematics folder must exist.
  • commands.yml may be omitted only when no schematic uses a COMMAND marker.

Generation policy

Configure start, placement, limits, checks, and paste behavior.

structure-version: 1
id: abandoned_mine
enabled: true

start:
  mode: MANUAL
  group: entrance

placement:
  native-facing: SOUTH
  offset:
    forward: 1
    left: 0
    right: 0
    up: 0

generation:
  mode: AUTOMATIC
  automatic:
    connector-order:
      primary: NEAREST_TO_ORIGIN
      secondary: FIFO
    job-delay: 40
  lookahead:
    enabled: true
    depth: 1
    connector-policy: ALL_CONNECTORS
  recovery:
    backtrack-on-blocked: false
  player-proximity:
    check-interval: 20t
    default-radius: 16
  limits:
    max-modules: 150
    max-radius: 300
    max-open-connectors: 40
  completion:
    require-all-connectors-resolved: true
    enter-closing-when-limits-reached: true

space-check:
  overlap:
    mode: SCHEMATIC_BOUNDING_BOX
    padding: 0
    double-pass-block-check: false
  block-check:
    enabled: true
    mode: WHITELIST
    replaceable:
      - AIR
      - CAVE_AIR
      - STONE
      - DEEPSLATE
      - TUFF
  post-paste-replacements:
    REDSTONE_BLOCK: AIR

performance:
  paste:
    mode: CHUNKED
    max-blocks-per-tick: 1500
    paste-air: false
    paste-entities: false
    max-active-jobs-per-instance: 1

Start and facing

start.mode must remain MANUAL in version 1. start.group must exist. native-facing is the forward direction used while authoring the schematics and accepts NORTH, EAST, SOUTH, or WEST.

Placement offset

The default forward: 1 places a child origin one block beyond its parent connector, which prevents touching marker positions from making the two full bounding boxes overlap. Horizontal values must be zero or positive; up may also be negative. Offsets affect connector expansion, not the initial manual start position.

Generation mode

AUTOMATIC processes open connectors after the configured stable delay. To make expansion player-driven, change the mode and keep a positive trigger radius:

generation:
  mode: PLAYER_PROXIMITY
  player-proximity:
    check-interval: 20t
    default-radius: 16

Each saved trigger activates only its own connector. The player must be in the same world. Proximity jobs still obey the global stability governor and placement checks.

Module selection

Map marker group ids to weighted candidates and safe exits.

groups-version: 1

groups:
  entrance:
    entries:
      - schematic: entrance_01.schem
        weight: 100

  corridor:
    entries:
      - schematic: corridor_01.schem
        weight: 80
      - schematic: corridor_small_01.schem
        weight: 20
        offset:
          forward: 0
          left: 0
          right: 0
          up: 0
        replacements:
          CONNECTOR: LIGHT_GRAY_CONCRETE
    fallback-groups:
      - corridor_fallback
    closing-groups:
      - corridor_end

  corridor_fallback:
    entries:
      - schematic: corridor_small_01.schem
        weight: 100
    closing-groups:
      - corridor_end

  corridor_end:
    entries:
      - schematic: collapsed_end_01.schem
        weight: 100

Weights

Weights are positive relative values, not required percentages. An 80/20 pair expresses a four-to-one preference while preserving the existing weighted-selection behavior.

Fallback groups

The connector's primary group is tried first. If every candidate fails placement or preflight, fallback groups are tried in their listed order. If all permitted candidates fail, the connector becomes BLOCKED; already generated modules are retained.

Closing groups

When limits cause the instance to enter CLOSING, each remaining connector uses its closing groups. Every schematic reachable from a closing group must be an endpoint with zero CONNECTOR markers. Completion is possible only when every connector is used or closed and no active or recoverable job remains.

Per-entry controls

  • offset replaces the pack placement offset only for that schematic entry.
  • replacements may override ORIGIN, CONNECTOR, or COMMAND marker replacement materials. Omitted keys keep global values.
  • allow-overlap-with-parent: true is intended only for small detail modules deliberately pasted inside their direct parent. It never permits overlap with unrelated modules or pending jobs, and the block whitelist still applies.

Optional post-paste actions

Connect COMMAND markers to weighted console command groups.

commands-version: 1

groups:
  spawn_loot:
    entries:
      - weight: 8
        commands:
          - "loot spawn {x} {y} {z} loot minecraft:chests/simple_dungeon"
      - weight: 2
        commands:
          rare: "loot spawn {x} {y} {z} loot minecraft:chests/ancient_city"

Each marker selects one weighted entry. That entry may contain one command, a list, or a named map. Commands run as console after durable module finalization in automatic mode, or when the marker's saved trigger activates in proximity mode.

Available placeholders include {world}, transformed {x}/{y}/{z} and signed offsets such as {y+1}, plus {instance}, {module}, {schematic}, {group}, {source_group}, {uuid}, and structure-origin coordinates.

Dispatch is at-most-once: the command record is marked consumed and persisted before Paper receives the command. A crash in that narrow interval can skip the command, but CoreStructuresX will not intentionally replay an external side effect after restart.

Placement safety

Start conservative, then loosen only the check that blocks an intentional design.

Bounding boxes

SCHEMATIC_BOUNDING_BOX protects generated modules and queued, running, or paused jobs across every structure instance in the same world. Reduce excess schematic air before adding exceptions.

Block whitelist

When enabled, every target paste block must currently be one of the listed materials. Include only terrain the structure is meant to replace.

Lookahead

Start at depth 1. ALL_CONNECTORS requires every new connector to have a simulated continuation; ANY_CONNECTOR requires at least one. Global node and time limits bound the search.

Projected limits

Pending jobs and the connectors they will create count toward module and open-connector caps. Candidates are rejected before paste when their projected result exceeds a hard limit.

  • Keep generation.recovery.backtrack-on-blocked: false. Setting it to true is rejected because the prior world, NBT, entities, commands, and later player changes cannot be restored losslessly.
  • Keep max-active-jobs-per-instance: 1 until the pack works correctly in serial execution.
  • Enable double-pass overlap only together with block checking and a deliberate replaceable whitelist. It cannot bypass pending jobs.
  • Use post-paste-replacements for temporary authoring blocks that should not remain in the final world.

Controlled rollout

Reload, validate, inspect, and only then expand.

  1. Make sure no paste job is queued, running, paused, or finalizing.
  2. Reload pack definitions and validate the exact pack:
/csx reload
/csx validate pack abandoned_mine
/csx packs list
  1. Fix every reported file path, field, group, marker, schematic, limit, or closing-group error.
  2. Start a small instance in an empty staging area with debug and actionbar feedback:
/csx start abandoned_mine automatic debug actionbar
  1. Read the returned instance id and inspect it while it expands:
/csx instance info <instance-id>
/csx instance pause <instance-id>
/csx instance resume <instance-id>

Use destructive stop only after paste work has finished. Reload and stop operations are rejected while abandoning a paste could leave world and journal state inconsistent.

Troubleshooting

Read the first concrete validation or blocked reason.

SymptomCheck firstTypical correction
Pack is not listedFolder location, manifest id, duplicate idsPlace it under packs/, match the folder and id, then reload.
Schematic is invalidOrigin count, marker type, line 3 group, line 4 radiusUse zero or one origin, a real group id, and only blank or positive marker radii.
Candidate overlapsFull selection bounds and nearby pending jobsShrink excess air, move markers, add a smaller fallback, or use a carefully bounded parent-detail exception.
Block whitelist rejectsThe first target material outside replaceableAdd only intentionally replaceable terrain or move the test location.
Lookahead rejectsNext-step space, connector policy, fallback endpointsAdd smaller continuations, start at depth 1, or choose ANY_CONNECTOR only when partial continuation is intended.
Instance becomes BLOCKED/csx instance info, connector reason, limitsRepair the primary/fallback/closing graph; do not enable destructive backtracking.

Before production

Prove the complete pack, not only the first module.

  • /csx validate reports zero errors and /csx packs list marks the pack valid.
  • Every connector line 3 resolves to a group; every command marker resolves to a command group.
  • Every closing path reaches only zero-connector endpoint schematics.
  • Every enabled rotation preserves rails, stairs, wall connections, containers, decorative signs, spawners, skulls, banners, and lecterns used by the pack.
  • Automatic delay and proximity triggers behave correctly after a restart.
  • Fallbacks handle tight terrain and lookahead rejection without leaving avoidable blocked connectors.
  • Module, radius, connector, block, chunk-load, time, and lookahead limits are tested with the largest intended structure.
  • Optional schematic entities are tested on the target Paper and WorldEdit/FAWE build before enabling paste-entities.
  • Two different instances are tested near one another to confirm cross-instance overlap protection.
  • Instance data is backed up before production-scale tests, and start permission remains restricted to trusted administrators.
